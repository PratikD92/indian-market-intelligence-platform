# ADR-014: Use OpenTelemetry, Prometheus, and Grafana for Infrastructure Observability

**Status:** Accepted

**Date:** 2026-08-23

## Context

The platform runs multiple microservices on GKE and requires end-to-end visibility into infrastructure health, service performance, and benchmark execution. Infrastructure monitoring must remain separate from AI-specific evaluation and observability.

## Decision

Adopt a layered infrastructure observability stack.

- **OpenTelemetry** for instrumentation across all microservices.
- **Prometheus** for collecting and storing infrastructure and service metrics.
- **Grafana** for dashboards and visualization.

This stack monitors all application microservices, while benchmark workloads consume the same telemetry for performance verification.

| Layer | Tool | Responsibility |
|-------|------|----------------|
| Instrumentation | OpenTelemetry | Collect traces, metrics, and logs from microservices. |
| Metrics Storage | Prometheus | Store infrastructure and service metrics. |
| Dashboards | Grafana | Visualize CPU, memory, network, latency, service health, and benchmark dashboards. |

## Consequences

### Advantages

- End-to-end visibility across distributed microservices.
- Unified infrastructure metrics and dashboards.
- Supports benchmark validation and production troubleshooting.
- Vendor-neutral observability through OpenTelemetry.

### Trade-offs

- Additional monitoring infrastructure.
- Instrumentation overhead across services.
- Requires consistent telemetry standards.

## Alternatives Considered

| Alternative | Reason Rejected |
|------------|-----------------|
| Google Cloud Operations Suite | Rejected because it provides strong infrastructure monitoring but offers less flexibility than an OpenTelemetry-based observability stack for a portable, production-grade microservices architecture. |
