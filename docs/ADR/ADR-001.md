# ADR-001: Adopt Microservices Architecture

**Status:** Accepted

**Date:** 2026-08-16

## Context

The platform combines independent capabilities including market data ingestion, knowledge synchronization, AI research, report generation, and benchmark execution. These workloads have different scaling, deployment, and reliability requirements, making a single deployable unit unsuitable for a production-grade system targeting 1M MAU.

## Decision

Adopt a **microservices architecture** on **Google Kubernetes Engine (GKE)** with clear service boundaries.

- **gRPC** for synchronous service-to-service communication.
- **Google Pub/Sub** for asynchronous event-driven communication.
- **Cloud Service Mesh (Istio-based)** for secure and observable inter-service networking.
- Each business capability is independently deployable and scalable.

## Consequences

### Advantages

- Independent deployment and scaling.
- Clear ownership per business capability.
- Fault isolation between services.
- Supports production-grade observability and resilience.

### Trade-offs

- Increased operational complexity.
- More network communication between services.
- API contract and version management become necessary.

## Alternatives Considered

| Alternative | Reason Rejected |
|------------|-----------------|
| Monolith | Limited scalability and fault isolation. |
| Modular Monolith | Insufficient for demonstrating distributed production architecture. |
| Serverless-only | Less suitable for long-running workflows and service mesh capabilities. |
