# ADR-004: Use gRPC for Synchronous Service Communication

**Status:** Accepted

**Date:** 2026-08-19

## Context

The platform consists of multiple internal microservices that require low-latency, request-response communication. Internal calls should be efficient, strongly typed, and integrate seamlessly with Cloud Service Mesh.

## Decision

Use **gRPC** for all synchronous service-to-service communication.

- Protocol Buffers for API contracts.
- Unary RPC as the default communication pattern.
- Cloud Service Mesh provides mTLS, retries, and traffic management.
- Public clients continue to use HTTPS through the API Gateway.

## Consequences

### Advantages

- Low-latency binary communication.
- Strongly typed contracts with Protocol Buffers.
- Efficient inter-service communication.
- Native integration with Cloud Service Mesh.

### Trade-offs

- Requires Protocol Buffer definitions.
- Less human-readable than REST.
- Browser clients cannot call gRPC directly without additional tooling.

## Alternatives Considered

| Alternative | Reason Rejected |
|------------|-----------------|
| REST | Higher serialization overhead for internal communication. |
| GraphQL | Better suited for client-facing APIs than internal service communication. |
| Message-only communication | Unsuitable for request-response interactions requiring immediate results. |
