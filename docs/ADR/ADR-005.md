# ADR-005: Use Google Pub/Sub for Asynchronous Event Communication

**Status:** Accepted

**Date:** 2026-08-20

## Context

Several platform workflows continue independently after an action completes. Examples include triggering knowledge synchronization after market data ingestion and notifying users after report generation. These workflows require loose coupling, retries, and independent scaling without blocking the originating service.

## Decision

Use **Google Pub/Sub** for asynchronous event-driven communication between microservices.

- Publish domain events instead of calling downstream services directly.
- Consumers process events independently.
- Retry and Dead Letter Queue (DLQ) handle failed event processing.
- Use events only for asynchronous workflows; synchronous operations continue to use gRPC.

Current events include:

- `DataIngested`
- `ReportCompleted`

## Consequences

### Advantages

- Decouples producers from consumers.
- Enables independent scaling of event consumers.
- Built-in retries and DLQ improve reliability.
- New consumers can subscribe without changing producers.

### Trade-offs

- Event contracts require version management.
- Debugging asynchronous flows is more complex.

## Alternatives Considered

| Alternative | Reason Rejected |
|------------|-----------------|
| Direct gRPC calls | Tightly couples asynchronous workflows. |
| Apache Kafka | Additional operational overhead for a GCP-first architecture. |
| Database polling | Higher latency and inefficient resource usage. |
