# ADR-009: Use pgvector for Semantic Retrieval

**Status:** Accepted

**Date:** 2026-08-21

## Context

The platform requires semantic search over financial documents, reports, filings, transcripts, and other normalized content. Users should retrieve relevant information based on meaning rather than exact keyword matches while keeping embeddings closely integrated with the primary data store.

## Decision

Use **pgvector** as the vector store for semantic retrieval.

- Knowledge Sync Service generates embeddings after content-specific chunking.
- Embeddings are stored in **pgvector** alongside references to PostgreSQL records.
- Semantic search retrieves relevant chunks before GraphRAG performs relationship-aware reasoning.
- PostgreSQL remains the source of truth; pgvector serves as the semantic index.

## Consequences

### Advantages

- Native integration with PostgreSQL.
- Eliminates the need for a separate vector database.
- Supports efficient similarity search.
- Maintains traceability between embeddings and source records.

### Trade-offs

- Vector indexes require additional storage.
- Large-scale vector workloads may require index tuning and optimization.

## Alternatives Considered

| Alternative | Reason Rejected |
|------------|-----------------|
| Vertex AI Vector Search | Rejected to keep semantic retrieval tightly integrated with PostgreSQL/pgvector, reduce infrastructure complexity and operational cost,
| Dedicated vector database | Additional infrastructure without sufficient benefit for this architecture. |
| PostgreSQL without vectors | Cannot support semantic similarity search. |
| Embeddings only in GraphRAG | Weak fit for nearest-neighbor semantic retrieval. |
